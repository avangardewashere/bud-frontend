Theory

0/4

Everything so far has been stateless. The moment a database enters the picture, the ephemerality you've been relying on becomes the problem instead of the feature.

The writable layer dies. Anything a volume is mounted over doesn't, because it was never in the container's filesystem to begin with — reads and writes at that path go somewhere else entirely. A volume is a hole punched through the container.

A named volume is storage Docker creates and manages; you refer to it by name and don't care where it lives. A bind mount points at a specific path on your machine — that's what you used for source code in session 4. tmpfs lives in memory and never touches disk, which is right for secrets and scratch files.

On Linux it's a directory under Docker's data root. On macOS and Windows it's inside the Linux VM that Docker Desktop runs, so you can't just open it in Finder — which is also why bind mounts are slower there and why file-watching needed polling last session. The practical rule: reach volume contents through a container, not through your file browser.

For local development a containerized database is unambiguously good — disposable, version-pinned, identical for everyone on the team. In production it's a genuine tradeoff: you inherit responsibility for backups, upgrades, and the consequences of a mistyped prune. Managed databases exist because that responsibility is heavier than it looks.

Same shape as the nginx experiment in session 1, but now it's a database and it matters.

docker run -d --name db-none -p 27017:27017 mongo:7 docker exec db-none mongosh --quiet --eval 'db.notes.insertOne({ msg: "no volume" })' docker exec db-none mongosh --quiet --eval 'db.notes.find()' docker rm -f db-none docker run -d --name db-none -p 27017:27017 mongo:7 docker exec db-none mongosh --quiet --eval 'db.notes.find()'

Postgres: add -e POSTGRES_PASSWORD=dev and use psql -U postgres -c in place of mongosh --eval.

The volume is created for you if it doesn't exist, but creating it explicitly makes the dependency visible.

docker volume create app-data docker run -d --name db -p 27018:27017 -v app-data:/data/db mongo:7 docker exec db mongosh --quiet --eval 'db.notes.insertOne({ msg: "named volume" })' docker exec db mongosh --quiet --eval 'db.notes.find()'

Postgres mounts its data at /var/lib/postgresql/data instead of /data/db.

Run each of these against the volume-backed container, reading the data back after every one. The third is the interesting one: -v removes anonymous volumes, not named ones, so the data survives a command most people believe deletes it.

docker restart db && sleep 3 docker exec db mongosh --quiet --eval 'db.notes.find()' docker rm -f db docker run -d --name db -p 27018:27017 -v app-data:/data/db mongo:7 && sleep 3 docker exec db mongosh --quiet --eval 'db.notes.find()' docker rm -fv db docker run -d --name db -p 27018:27017 -v app-data:/data/db mongo:7 && sleep 3 docker exec db mongosh --quiet --eval 'db.notes.find()'

Save docker volume rm app-data for after the backup step — it's the one that actually works.

The Mounts field on the container is the one worth remembering — it tells you exactly what's persisted and what isn't, which is the first thing to check when data mysteriously disappears.

docker volume ls docker volume inspect app-data docker inspect db --format '{{json .Mounts}}'

A container that exists only to hold two mounts and run tar. Stop the database first — copying a running database's files gives you a corrupt archive, and that's the kind of backup that looks fine until you need it.

docker stop db docker run --rm -v app-data:/data -v "$(pwd)":/backup alpine \ tar czf /backup/app-data.tgz -C /data . docker volume create app-restored docker run --rm -v app-restored:/data -v "$(pwd)":/backup alpine \ tar xzf /backup/app-data.tgz -C /data docker run -d --name db-restored -p 27019:27017 -v app-restored:/data/db mongo:7 sleep 3 && docker exec db-restored mongosh --quiet --eval 'db.notes.find()'

This is a file-level copy. The real answer for a database is its own dump tool — mongodump or pg_dump — which can run against a live server and produces something you can restore across versions.

Scripts in that directory run only when the data directory is empty. Start it, confirm the seed data, then restart and confirm the script did not run again — that conditional is the whole behaviour, and forgetting it leads to "why won't my schema change apply".

docker run -d --name db-seed -p 27020:27017 \ -v app-seed:/data/db \ -v "$(pwd)/initdb:/docker-entrypoint-initdb.d:ro" \ mongo:7 sleep 4 docker exec db-seed mongosh appdb --quiet --eval 'db.items.find()' docker restart db-seed && sleep 4 docker logs db-seed | tail -20

Postgres reads .sql and .sh files from the same path, with the same empty-directory condition.

Point the database at a folder on your machine instead of a named volume. Depending on your OS this either works but slowly, or fails outright on file ownership or locking. Read the logs either way — the conclusion is the rule: bind mounts for source you edit, named volumes for data the database owns.

mkdir -p ./db-bind docker run -d --name db-bind -p 27021:27017 \ -v "$(pwd)/db-bind:/data/db" mongo:7 sleep 4 docker ps -a --filter name=db-bind docker logs db-bind | tail -20

Every -v /app/node_modules from session 4 left one behind, and database images declare their own. Look at the dangling list before pruning, and check nothing on it is something you want.

The two that cost people real data.

docker rm -v does not delete named volumes — only anonymous ones. People learn that -v means "and the volumes", conclude volume cleanup is automatic, and then reach for docker volume prune or docker system prune --volumes to tidy up. Those two do delete named volumes, including the database you were using ten minutes ago. There is no undo.

Anonymous volumes pile up invisibly. Every container started without a named volume for a path the image declares gets a fresh one, kept forever. Check docker volume ls occasionally rather than after your disk fills.
