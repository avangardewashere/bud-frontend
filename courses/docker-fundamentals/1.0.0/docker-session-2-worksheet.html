Theory

0/4

Session 1 was about running things. This one is about what you're running — where images come from, what they're made of, and how much disk they quietly consume.

An image is a stack of read-only layers. A running container adds one thin writable layer on top — which is exactly why the edit you made inside nginx last session vanished when you removed the container.

A tag is a mutable label pointing at an image. A digest is a hash of the content itself. node:22 means something different this month than last month; node@sha256:… never changes.

Docker Official Images, Verified Publisher, and everything else. Pulling a random image runs someone else's code on your machine with whatever it was built with. Skim the pull page for node and note who maintains it.

Images, stopped containers, volumes, and build cache — accounted for separately, reclaimed separately. Knowing which is which is the difference between freeing 8GB and deleting your database.

Hands-on

0/8

Most of these print information rather than change anything. Read the output properly — that's the whole skill this session is building.

Watch the pull output. Each line is one layer arriving.

docker pull node:22 docker pull node:22-slim docker pull node:22-alpine docker images node

Fill these in from the docker images output. You'll reuse this table in session 5 when you cut your own image down.

ImageSizeWould you ship it?
node:22
node:22-slim
node:22-alpine

Each row is one build instruction. The <missing> IDs are normal on a pulled image — you only get real IDs for layers built locally.

docker history nginx docker history node:22-alpine --no-trunc

Two names, one image ID, no extra disk used. Then remove your tag and confirm the image itself survives.

docker tag nginx:latest my-nginx:v1 docker images | grep nginx docker rmi my-nginx:v1 docker images | grep nginx

Get the digest, then pull that exact content. This is the form you'll use in production Dockerfiles and in CI.

docker image inspect nginx --format '{{index .RepoDigests 0}}' # paste the result: docker pull nginx@sha256:PASTE_DIGEST_HERE

Go templates. Ugly syntax, but it's how you get values into scripts and CI steps later.

docker image inspect node:22-alpine --format '{{.Config.WorkingDir}}' docker image inspect node:22-alpine --format '{{json .Config.Env}}' docker image inspect node:22-alpine --format '{{.Architecture}}/{{.Os}}'

The second pull says "Already exists" for the shared base. That reuse is why picking a consistent base across your projects saves real disk and real pull time.

docker pull nginx:alpine docker pull redis:alpine

Run df first and note the reclaimable column. Then prune only dangling images and run df again to see what changed. Do not add -a.

docker system df docker system df -v docker image prune docker system df

Deliverable

0/3

The cheat sheet is the point of this session. Copying one off the internet defeats it — the value is in writing the description, because that's when you find out which commands you didn't understand.

Group by what you're trying to do, not alphabetically: looking around, running things, inspecting, cleaning up. One line of plain description per command.

You're making this decision now so session 4 isn't a coin flip. There's a right answer for your stack and it depends on whether you use native modules.

The one command to be careful with today.

docker system prune -a removes every image not attached to a running container, plus your entire build cache. It's not destructive to your data, but your next build will start from nothing and take several minutes. Use plain docker image prune while you're learning.

Add --volumes to that and it is destructive — that's your database contents. Don't type it reflexively when a tutorial tells you to.
