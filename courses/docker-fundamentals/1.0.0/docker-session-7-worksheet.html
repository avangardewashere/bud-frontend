Networking and Docker Compose

Three services, one command. The most immediately useful session in the course — and the one where you finally stop typing eleven flags per container.

Theory40 min
Hands-on115 min
Deliverable45 min

Theory

0/4

Almost every confusing Docker bug you'll hit from here is an addressing bug. Get this block properly straight and the rest of your Docker life gets quieter.

Every container you've run so far landed on the default bridge network, where containers get IPs but cannot resolve each other by name. Create your own network and Docker gives it an embedded DNS server, so service names become hostnames. This is the single reason Compose always creates a network for your project.

Inside a container, localhost is that container's own loopback interface — not your machine, not a sibling container. An API configured with mongodb://localhost:27017 is looking for a database running inside itself. It isn't there. The address is db:27017, the service name.

Containers on a shared network reach each other on the container's own port whether or not it's published. -p exists purely to let things outside Docker in. So a database used only by your API needs no ports entry at all — and in production, actively shouldn't have one.

services are containers, volumes are the named volumes from last session, networks is usually implicit. depends_on controls order. healthcheck defines what "ready" means — and without one, depends_on only waits for a container to start, which is not the same thing at all.

Hands-on

0/9

Steps 1 and 2 are ten minutes of deliberate pain so that the Compose file in step 4 reads as relief rather than magic.

Two containers, same network, and the second cannot find the first. The error is bad address — remember what it looks like, because you'll see it again.

docker run -d --name db1 mongo:7 docker run --rm alpine ping -c 1 db1 docker inspect db1 --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'

Identical commands, one extra flag, and the name resolves. Then wire all three services by hand to feel how much bookkeeping this is.

docker network create appnet docker run -d --name db2 --network appnet mongo:7 docker run --rm --network appnet alpine ping -c 1 db2 docker network inspect appnet --format '{{range .Containers}}{{.Name}} {{end}}'

Come back to this after step 5, when the stack is up. Rows 6 and 7 are the ones that catch experienced developers: the browser is outside Docker entirely, so code running in it cannot use service names no matter where the page was served from.

Everything from sessions 3 through 6 in one place. Note the two different addresses for the same API: the server-side variable uses the service name, the public one uses localhost because the browser resolves it. Add a /health route to your API first — app.get("/health", (_req, res) => res.send("ok")).

compose.yaml

services: web: build: context: . args: NEXT_PUBLIC_API_URL: http://localhost:4000 ports: - "3000:3000" environment: API_URL: http://api:3000 depends_on: api: condition: service_healthy api: build: ./api ports: - "4000:3000" environment: MONGO_URL: mongodb://db:27017/appdb depends_on: db: condition: service_healthy healthcheck: test: ["CMD", "wget", "-qO-", "http://localhost:3000/health"] interval: 5s timeout: 3s retries: 5 start_period: 10s db: image: mongo:7 volumes: - app-data:/data/db healthcheck: test: ["CMD", "mongosh", "--quiet", "--eval", "db.adminCommand('ping')"] interval: 5s timeout: 3s retries: 10 volumes: app-data:

If your app talks to the database directly and has no separate API, drop the api service and point web at mongodb://db:27017. The lesson is the same.

Note what Compose named things: the network and volume are prefixed with your project name, which defaults to the directory. That prefix is why two projects can both have a service called db without colliding.

docker compose up -d --build docker compose ps docker network ls | grep -i "$(basename $PWD)" docker volume ls | grep -i "$(basename $PWD)"

Use compose exec to run commands from inside a service — that's how you check reachability from the container's point of view rather than yours.

docker compose exec api wget -qO- http://db:27017 docker compose exec api wget -qO- http://localhost:27017 docker compose exec web wget -qO- http://api:3000/health curl -s -o /dev/null -w "%{http_code}\n" localhost:3000 curl -s -o /dev/null -w "%{http_code}\n" localhost:27017

For rows 6 and 7, open the page in your browser and try both URLs from the devtools console.

There's no ports entry on db in that file, and the API still reaches it fine while your host can't touch it at all. That's the correct shape: exactly one service exposed, everything else reachable only from inside the network.

docker compose port db 27017 docker compose exec api wget -qO- --timeout=2 http://db:27017 docker compose ps --format "table {{.Service}}\t{{.Ports}}"

Replace the API's depends_on with the short form — just - db, no condition — then bring the stack up from cold. Compose starts the database and immediately starts the API, which tries to connect to a server still initialising and crashes. Put the healthcheck condition back and watch it wait instead.

docker compose down # edit compose.yaml: depends_on: [db] docker compose up -d --build docker compose logs api | tail -20 docker compose ps

These six commands are most of what you'll use from now on. The last pair is last session's lesson wearing a different hat: down keeps your named volumes, down -v deletes them. Same trap, new syntax.

docker compose logs -f api docker compose exec db mongosh docker compose restart api docker compose up -d --build web docker compose down docker compose down -v

Deliverable

0/3

A repo where docker compose up gives someone your entire working environment is a genuinely strong signal. It's also the thing you'll be most grateful for on your own machine in three months.

Clone, one command, working stack. Write the README as if for someone who has never seen the project, because that's who it's for — including you, later.

Three cases: container to container, host to container, and browser to container. Every future bug in this category is one of those three, and having written the rule once means you'll recognise it in seconds rather than an hour.

Remove db1, db2 and the appnet network from steps 1 and 2 — Compose manages its own now.

The two that will eat an afternoon.

localhost inside a container refers to that container. This is the most common Docker bug there is, and it's particularly nasty in a frontend project because the same variable can need two different values — api:3000 for code running on the server, localhost:4000 for code running in the browser. When a fetch works server-side and fails in the browser, this is why.

depends_on without a condition waits for the container to start, not for the service to be usable. Databases take seconds to accept connections. Your API starts instantly, fails to connect, and exits — and then you spend twenty minutes suspecting the connection string, which is correct.
