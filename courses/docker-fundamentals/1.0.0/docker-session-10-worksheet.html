Theory

0/4

Nine sessions of things working on machines you control completely. This one is about what happens when nobody is watching and something dies at 3am.

always restarts a container even after you deliberately stopped it and rebooted. unless-stopped respects a manual stop, which is almost always what you want. Both interact badly with memory limits: when the kernel kills a process for exceeding its limit the container exits 137, the policy restarts it, and it does the same thing again. A restart policy is not a fix for a container that can't stay up.

Writing a log file inside a container is a mistake in three ways: it grows the writable layer, docker logs can't see it, and it's destroyed with the container. Print to stdout and stderr and let the log driver deal with collection. Then set rotation, because the default json-file driver grows until the disk is full and a full disk takes everything down at once.

A reverse proxy holds ports 80 and 443, obtains and renews certificates, and forwards to your services by their Compose service names. Your app never sees a certificate and never needs to — which also means the addressing rule from session 7 is what makes this work. Certificates live in a volume; lose it and you re-issue, which is how people hit rate limits.

Compose on a single server handles far more traffic and far longer than people expect, and it fails in ways you can reason about. You graduate when you need more than one machine, zero-downtime rollouts, or autoscaling — that's what orchestration buys. It costs a control plane, a new vocabulary, and a much larger surface to get wrong. Knowing why you'd move is more valuable than moving early.

Hands-on

0/9

You need a small VPS and a domain pointed at it. The cheapest tier anywhere is enough. Set the DNS A record before you start so it has time to propagate.

Docker publishes ports by manipulating iptables directly, which on some setups bypasses the firewall — so never publish a database port on a public server and assume the firewall covers you. Session 7's lesson is now a security control rather than a tidiness preference.

curl -fsSL https://get.docker.com | sh sudo usermod -aG docker $USER sudo ufw default deny incoming sudo ufw allow OpenSSH sudo ufw allow 80,443/tcp sudo ufw enable sudo sed -i 's/^#*PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config sudo systemctl restart ssh

Confirm your SSH key works in a second terminal before you close the first one. Locking yourself out of a fresh box is survivable; locking yourself out of a running one is not.

A server that builds is a server that needs your source, your dev dependencies and enough RAM to run a bundler. The whole point of session 9 is that the artifact already exists. The IMAGE_TAG variable is how you'll roll back later.

/srv/app/compose.yaml — on the server

services: web: image: ghcr.io/YOUR_USER/YOUR_REPO:${IMAGE_TAG:-latest} restart: unless-stopped environment: NODE_ENV: production MONGO_URL: mongodb://db:27017/appdb depends_on: db: condition: service_healthy db: image: mongo:7 restart: unless-stopped volumes: - app-data:/data/db healthcheck: test: ["CMD", "mongosh", "--quiet", "--eval", "db.runCommand({ping:1})"] interval: 10s timeout: 3s retries: 10 volumes: app-data:
mkdir -p /srv/app && cd /srv/app echo "IMAGE_TAG=latest" > .env docker compose pull docker compose up -d docker compose ps

If the package is private, log in on the server with a read-only personal access token rather than the token you use anywhere else.

Two lines of configuration and certificates appear by themselves. Note that web now has no published ports at all — Caddy reaches it by service name, and the only thing listening on the public internet is the proxy. The caddy-data volume holds your certificates; back it up or accept re-issuing them.

/srv/app/Caddyfile

app.yourdomain.com { reverse_proxy web:3000 }

compose.yaml — add the proxy

caddy: image: caddy:2-alpine restart: unless-stopped ports: - "80:80" - "443:443" volumes: - ./Caddyfile:/etc/caddy/Caddyfile:ro - caddy-data:/data - caddy-config:/config depends_on: - web volumes: app-data: caddy-data: caddy-config:
docker compose up -d docker compose logs -f caddy curl -I https://app.yourdomain.com

Kill the container and watch it come back within seconds. Then stop it deliberately and watch it stay down — that's the difference between unless-stopped and always, and it's worth seeing rather than reading.

compose.yaml — on the web service

deploy: resources: limits: memory: 512M cpus: "0.75" healthcheck: test: ["CMD", "wget", "-qO-", "http://localhost:3000/api/health"] interval: 30s timeout: 5s retries: 3 start_period: 20s
docker compose up -d docker stats --no-stream docker compose kill web && sleep 8 && docker compose ps docker compose stop web && sleep 8 && docker compose ps docker compose start web

Exit code 137 and OOMKilled: true. Do this in a throwaway container rather than your live service. The point is recognising the signature — a container that keeps restarting with 137 is being killed for memory, not crashing on a bug, and no amount of code reading will show you that.

docker run --name oom -m 64m node:22-alpine \ node -e "const a=[]; while(true) a.push(Buffer.alloc(1048576))" docker inspect oom --format '{{.State.OOMKilled}} {{.State.ExitCode}}' docker rm oom

Thirty megabytes per service, ceiling enforced. Without this, a chatty service on a small box fills the disk in weeks and everything stops at once — including your ability to SSH in and fix it.

compose.yaml — on every service

logging: driver: json-file options: max-size: "10m" max-file: "3"
docker compose up -d docker compose logs --tail 20 web sudo du -sh /var/lib/docker/containers df -h /

A read-only root filesystem is the strongest single control here, and it will break your app the first time — Next.js needs a writable cache directory, so that goes in a tmpfs. Apply these one at a time and load the site after each, or you won't know which one caused the failure.

compose.yaml — on the web service

read_only: true tmpfs: - /tmp - /app/.next/cache cap_drop: - ALL security_opt: - no-new-privileges:true
docker compose up -d web docker compose logs web | tail -20 curl -I https://app.yourdomain.com docker compose exec web whoami

The deploy job writes the SHA tag into the server's .env, pulls, and restarts. Deploying by SHA rather than latest is what makes rollback a one-line edit instead of a rebuild. Verify the tag format against your packages page first — the metadata step abbreviates the SHA.

.github/workflows/container.yml — new job

deploy: needs: [image, test] if: github.ref == 'refs/heads/main' runs-on: ubuntu-latest steps: - name: Pull and restart on the server uses: appleboy/ssh-action@v1 with: host: ${{ secrets.DEPLOY_HOST }} username: ${{ secrets.DEPLOY_USER }} key: ${{ secrets.DEPLOY_SSH_KEY }} script: | cd /srv/app echo "IMAGE_TAG=sha-$(echo ${{ github.sha }} | cut -c1-7)" > .env docker compose pull docker compose up -d docker image prune -f
# then prove rollback works, on the server: cat .env echo "IMAGE_TAG=sha-PREVIOUS" > .env docker compose up -d curl -I https://app.yourdomain.com

Most of this was already done in earlier sessions — that's the point of running the audit at the end rather than treating hardening as a separate phase. Mark anything you skipped honestly; a deferred control you know about is fine, one you've forgotten isn't.

Deliverable

0/3

Last one. What you're producing here is the thing you point at when someone asks whether a frontend developer can ship infrastructure.

Live URL, the architecture in four or five lines, the pipeline, the deploy flow, and the image size and build-time numbers you measured in sessions 5 and 9. Numbers you took yourself read as engineering; adjectives read as a tutorial.

Deploy, roll back, read logs, restore the database. Write it for yourself at 2am with no context. Everything in it is a command you ran this session or in session 6, so this is transcription rather than invention, and it's the single most useful page in the repo.

Four onward paths: Kubernetes for orchestration, Terraform to provision the box you just configured by hand, Prometheus and Grafana for observability, or image signing and SBOMs for supply chain. Pick one and write down why — a decision with a reason behind it outlasts a list of options.

Three things to know before you leave this running.

Docker writes its own iptables rules, so a published port can be reachable from the internet even when your firewall says otherwise. The protection that actually holds is not publishing the port in the first place — which is why the database has no ports entry.

The caddy-data volume holds your certificates and their renewal state. Delete it casually and you re-request certificates, and Let's Encrypt rate limits are per-domain and per-week. Treat it like the database volume.

You now own a database. Session 6 gave you the backup command; nothing runs it on a schedule unless you set that up. An untested backup is a guess, so restore it once into a throwaway container and confirm the data is really there.
