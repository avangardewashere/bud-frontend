Theory

0/4

Three sessions of generic Docker. This is where it meets what you actually build — and where frontend containers turn out to have their own set of problems.

A dev container optimizes for feedback speed: source mounted from your machine, dev server running, dependencies installed including the dev ones. A production container optimizes for size and immutability: nothing mounted, source already compiled, no dev tooling. There is no single file that does both well.

A Vite or CRA build produces files. It needs a web server, and once built, Node is not involved at all. Next.js with SSR produces a Node process that has to stay alive to render requests. Which one you have decides the base image, the command, and the port.

Plain next start needs the whole project directory present. output: "standalone" traces only the files the server actually imports and emits a self-contained folder — that's the one that makes small images possible. output: "export" gives you static files and drops server features. You'll use next start today and switch to standalone in session 5.

Anything prefixed NEXT_PUBLIC_ gets inlined into the JavaScript bundle when you build. It is a string in a file, not a variable read at startup — so passing a different value with -e at run time changes nothing. Server-only variables have no such problem. This is the single most confusing thing about containerizing Next.js.

Hands-on

0/9

Use a real app of your own. Commands below assume a Next.js project and port 3000 — adjust the port if yours differs. On PowerShell, swap $(pwd) for ${PWD}.

The dev server runs inside the container; the code comes from your machine. Then edit a component and watch the browser.

Dockerfile.dev

FROM node:22-alpine WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . EXPOSE 3000 CMD ["npm", "run", "dev"]
docker build -f Dockerfile.dev -t myweb:dev . docker run --rm -it -p 3000:3000 -v "$(pwd):/app" myweb:dev

That mount replaced the container's entire /app — including the node_modules the build installed. If it started at all, it's using your host's copy. The empty anonymous volume masks that one path so the container keeps its own. Add .next too, so container build output doesn't land in your working tree.

docker run --rm -it -p 3000:3000 \ -v "$(pwd):/app" \ -v /app/node_modules \ -v /app/.next \ myweb:dev

Filesystem events often don't cross the boundary into the container's VM, so the dev server never learns your file changed. Polling fixes it at the cost of some CPU. Which variable applies depends on the bundler your dev server uses — try these, and write down which one worked.

docker run --rm -it -p 3000:3000 \ -v "$(pwd):/app" -v /app/node_modules -v /app/.next \ -e WATCHPACK_POLLING=true \ -e CHOKIDAR_USEPOLLING=true \ myweb:dev

One stage, dev dependencies installed because the build needs them, source copied in, built inside the image. It works, and it's much bigger than it needs to be. Leave it that way.

Dockerfile

FROM node:22-alpine WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . ARG NEXT_PUBLIC_API_URL ENV NEXT_PUBLIC_API_URL=$NEXT_PUBLIC_API_URL RUN npm run build ENV NODE_ENV=production EXPOSE 3000 CMD ["npm", "start"]
docker build --build-arg NEXT_PUBLIC_API_URL=https://built-at-build-time.example -t myweb:prod .

This number is your baseline. Session 5 is graded against it, so put it somewhere you'll find again.

docker run -d -p 3000:3000 --name web myweb:prod docker images myweb curl -s -o /dev/null -w "%{time_total}s\n" localhost:3000

Render process.env.NEXT_PUBLIC_API_URL somewhere visible in a client component. Then start the container with a different value and load the page. It still shows the build-time string — the run-time one is ignored, because there's no variable left to read.

docker rm -f web docker run -d -p 3000:3000 --name web \ -e NEXT_PUBLIC_API_URL=https://set-at-run-time.example \ myweb:prod # then open localhost:3000 and read the value

Only relevant if you also ship static builds — but the routing bug catches everyone once. Load a nested route directly and nginx returns 404, because there is no file at that path. try_files hands every unmatched request to index.html and lets the router take over. This is also the one place today you'll need two FROM lines; session 5 explains why.

nginx.conf

server { listen 80; root /usr/share/nginx/html; index index.html; location / { try_files $uri $uri/ /index.html; } }

Dockerfile.static

FROM node:22-alpine AS build WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . RUN npm run build FROM nginx:alpine COPY --from=build /app/dist /usr/share/nginx/html COPY nginx.conf /etc/nginx/conf.d/default.conf
docker build -f Dockerfile.static -t myweb:static . docker run -d -p 8080:80 --name static myweb:static curl -I localhost:8080/some/nested/route

Check the dev dependencies row with docker run --rm myweb:prod ls node_modules and look for something like eslint or typescript.

Deliverable

0/3

Two working Dockerfiles for an app that's actually yours. That's the first thing in this course a reviewer could look at and take seriously.

The mount flags are the part you'll forget. Put the full dev command in the README, not in your shell history.

For each variable your app uses: does it have to be known at build time, or can it be supplied at startup? Getting this list right now saves you a genuinely nasty debugging session in session 8.

The two that will cost you the most time.

Mounting your project over /app hides everything the image built there. If the container starts and immediately complains it can't find a module, or crashes on a native binary, that's your host node_modules being used inside Alpine Linux. The anonymous volume in step 2 is the fix, and you will need it on every project.

Hot reload failing silently is not a Docker error — nothing logs, the page simply never updates. Reach for the polling flags before you start rewriting your dev setup.
