Docker in CI/CD with GitHub Actions

Your machine stops being where images get built. By the end there's a package on your GitHub profile that a pipeline built, tested, scanned and published without you touching it.

Theory40 min

Theory

0/4

Everything so far is reproducible on one machine. A pipeline makes it reproducible without one, which is the actual point of containers.

The image that passes your tests is the image that reaches production — not a rebuild from the same commit, the identical bytes. Rebuilding per environment reintroduces exactly the drift containers exist to eliminate, and it's why session 8's config split matters: one image, different environment at startup.

Back to session 2: a tag is a movable pointer. latest tells you nothing about what's running — two people pulling it an hour apart can get different images. A sha-abc1234 tag maps one image to one commit permanently, which is what you need when production is broken and you want to know what is actually deployed.

Every workflow run gets a GITHUB_TOKEN automatically, but it starts read-only. Pushing a package needs packages: write declared on the job. No personal access token, no stored secret — the right shape, and worth noticing after session 8.

Actions can run a database alongside your job. The catch: if your steps run directly on the runner, the service is at localhost on its mapped port, because the port is published to the runner host. If the job itself runs inside a container, you address it by service name instead. Same distinction as session 7, different clothing.

Hands-on

0/9

Work on a branch and open a pull request, so every push gives you feedback without touching main. Action versions below were current when this was written; check for newer majors as you go.

No push, no tests, no cache. Confirm your Dockerfile builds on a machine that isn't yours, which catches anything you accidentally relied on locally. Record this run's duration as row 1.

.github/workflows/container.yml

name: container on: push: branches: [main] pull_request: jobs: image: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: docker/setup-buildx-action@v3 - uses: docker/build-push-action@v6 with: context: . push: false tags: app:ci

Two lines. The first run after adding them is still cold — it's the second that shows the benefit, so push an empty commit to trigger one. This is session 3's caching lesson operating across machines instead of across builds.

cache-from: type=gha cache-to: type=gha,mode=max
git commit --allow-empty -m "trigger cached run" git push

Five rows, filled as you add each stage. Rows 1 and 2 are the cache measurement; the rest tell you what each safety net costs in wall-clock time, which is the number that decides whether a pipeline gets used or worked around.

RunDurationResult and notes
1. Build only, cold
2. Build only, cached
3. Tests on a service container
4. Vulnerability scan added
5. Pushed to GHCR

One action produces the whole tag set from the event: a SHA tag always, a PR tag on pull requests, and latest only on the default branch. Read the step's output in the log to see exactly what it generated.

- name: Derive tags id: meta uses: docker/metadata-action@v5 with: images: ghcr.io/${{ github.repository }} tags: | type=sha,prefix=sha- type=ref,event=pr type=raw,value=latest,enable={{is_default_branch}}

Two build steps, deliberately. The first loads a single-architecture image onto the runner so the scanner has something local to inspect. The second pushes and hits the cache, so it costs seconds. You can't combine load with a multi-platform build, which is why this shape is standard.

.github/workflows/container.yml — the image job

image: runs-on: ubuntu-latest permissions: contents: read packages: write steps: - uses: actions/checkout@v4 - uses: docker/setup-qemu-action@v3 - uses: docker/setup-buildx-action@v3 - name: Log in to GHCR if: github.event_name != 'pull_request' uses: docker/login-action@v3 with: registry: ghcr.io username: ${{ github.actor }} password: ${{ secrets.GITHUB_TOKEN }} - name: Derive tags id: meta uses: docker/metadata-action@v5 with: images: ghcr.io/${{ github.repository }} tags: | type=sha,prefix=sha- type=ref,event=pr type=raw,value=latest,enable={{is_default_branch}} - name: Build for scanning uses: docker/build-push-action@v6 with: context: . load: true tags: app:ci cache-from: type=gha cache-to: type=gha,mode=max build-args: | NEXT_PUBLIC_API_URL=${{ vars.NEXT_PUBLIC_API_URL }} - name: Scan for vulnerabilities uses: aquasecurity/trivy-action@0.28.0 with: image-ref: app:ci severity: HIGH,CRITICAL ignore-unfixed: true exit-code: "1" - name: Build and push if: github.event_name != 'pull_request' uses: docker/build-push-action@v6 with: context: . platforms: linux/amd64,linux/arm64 push: true tags: ${{ steps.meta.outputs.tags }} labels: ${{ steps.meta.outputs.labels }} cache-from: type=gha build-args: | NEXT_PUBLIC_API_URL=${{ vars.NEXT_PUBLIC_API_URL }}

Set NEXT_PUBLIC_API_URL under Settings, then Actions, then Variables. It's configuration rather than a secret, and it belongs where session 8 concluded it belongs.

A second job with a service container. Note the connection string uses localhost — these steps run on the runner, and the service's port is published to it. The healthcheck options are the same idea as session 7's, expressed in Actions syntax.

.github/workflows/container.yml — the test job

test: runs-on: ubuntu-latest services: mongo: image: mongo:7 ports: - 27017:27017 options: >- --health-cmd "mongosh --quiet --eval 'db.runCommand({ping:1})'" --health-interval 5s --health-timeout 3s --health-retries 10 steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: node-version: 22 cache: npm - run: npm ci - run: npm test env: MONGO_URL: mongodb://localhost:27017/test

With exit-code: "1" a high-severity finding stops the pipeline. Try it against a deliberately old base image to see a real failure, then read the report. ignore-unfixed matters: blocking on vulnerabilities with no available patch means blocking forever, which teaches people to disable the scan.

docker run --rm aquasec/trivy image node:18-alpine --severity HIGH,CRITICAL

Delete packages: write, merge to main, and watch the push fail with a denial that says nothing about permissions. This is the single most common first-time GHCR failure, and recognising the message saves you a long search.

gh run view --log-failed # then put the permissions block back and re-run

New GHCR packages are private by default, so link the package to the repository and set its visibility in the package settings if you want it visible on your profile. Then pull it by SHA tag and run it — this is the artifact session 10 deploys, and confirming it runs on your machine first is worth two minutes.

docker pull ghcr.io/YOUR_USER/YOUR_REPO:latest docker image inspect ghcr.io/YOUR_USER/YOUR_REPO:latest --format '{{.Architecture}}' docker run --rm -p 3000:3000 ghcr.io/YOUR_USER/YOUR_REPO:latest

Deliverable

0/3

A green badge on a repo that builds, tests, scans and publishes a container is a stronger signal than most frontend portfolios carry. It's also the thing to point at in an interview.

Badge plus two sentences on what the pipeline does. Someone skimming your repo should understand the whole thing without opening the YAML.

![container](https://github.com/YOUR_USER/YOUR_REPO/actions/workflows/container.yml/badge.svg)

Which tags get created, which one a deploy references, and how you'd roll back. Write it before session 10 needs it, because "which image do I actually deploy" is the first question that session asks.

Rows 1 and 2 of the ledger. It's a concrete engineering result and it belongs next to the image size numbers from session 5.

Two that will stop your first push.

Without permissions: packages: write on the job, the push fails with a denial about installation or access rather than anything mentioning permissions. The default token is read-only and nothing warns you until the very last step, after a full build.

A cache is not a guarantee. type=gha caches are scoped per branch with fallback to the default branch, and GitHub evicts them under a size limit, so a run you expected to be fast occasionally isn't. Don't treat a slow run as a broken pipeline until you've checked whether the cache was there.
