Theory

0/4

Last session ended with you listing everything in the image that a running server has no use for. Every idea here exists to delete one item from that list.

Each FROM starts a fresh image. COPY --from=builder reaches into an earlier stage and takes specific paths out of it. Only the final stage becomes your image — everything else is scaffolding that gets thrown away, so its size stops mattering entirely.

Alpine is smallest but uses musl instead of glibc, which breaks some prebuilt native binaries. Slim is Debian with glibc — bigger, fewer surprises. Distroless has no shell at all, which is excellent for security and miserable when you need to debug a running container. There's no universally right answer, only a right answer for your dependency list.

Layer caching reuses a whole step's result. A BuildKit cache mount gives one RUN a persistent scratch directory that survives between builds but is never committed into the image. That's how you keep the npm download cache without shipping it. Stages with no dependency on each other also build in parallel.

Default is uid 0 inside the container. That's not the same as root on the host, but it removes a whole layer of defence, and any mounted host path is writable by it. One USER line closes it. Doing this now also means session 10's hardening checklist is already half done.

Next traces which files the server genuinely imports and writes a self-contained folder. Build locally once and look at what appeared in .next/standalone before you containerize it — it's a much smaller tree than you'd guess. Dependencies, build, run. The runner starts from a clean base and receives only three paths. Note that public may not exist in your project — if the build fails on that line, delete it.

Add USER node just above EXPOSE and rebuild with no other change. The copied files still belong to root, so the server can't write its cache and fails at startup. Read that error before fixing it — permission errors in containers look alarming and are almost always this.

Change only the last FROM to node:22-slim and rebuild. It'll be noticeably larger. The question isn't which is smaller — it's whether the alpine one runs your app correctly, including image optimization and anything with a compiled dependency.

docker build -t myweb:slim . docker images myweb docker run --rm -d -p 3002:3000 --name web4 myweb:slim curl -s -o /dev/null -w "%{http_code}\n" localhost:3002

Delete the lockfile-derived cache from the equation: change the dependency line and rebuild twice, deleting the builder cache in between with docker builder prune. The npm download cache persists outside the image, so the second run doesn't refetch the tarballs.

Dockerfile — deps stage

FROM node:22-alpine AS deps WORKDIR /app COPY package*.json ./ RUN --mount=type=cache,target=/root/.npm npm ci

Your machine builds for its own CPU by default. Most cloud VMs are amd64. Locally this problem hides, because Docker will emulate the other architecture — slowly and silently. The failure only shows up on the server, as an exec format error, at the worst possible moment. Build both and read the field.

docker image inspect myweb:v3 --format '{{.Architecture}}' docker build --platform linux/amd64 -t myweb:amd64 . docker image inspect myweb:amd64 --format '{{.Architecture}}'

Where alpine bites.

Alpine uses musl rather than glibc, so packages shipping prebuilt binaries — sharp, bcrypt, canvas, anything wrapping a C library — may install fine and then fail at run time. RUN apk add --no-cache libc6-compat in the runner stage resolves many of these. If you're fighting it for more than twenty minutes, switch to slim and move on; forty extra megabytes is cheaper than an afternoon.

Also worth knowing: the build succeeding tells you nothing here. These failures happen when the code runs, so always load an actual page before you record a size and call it done.
