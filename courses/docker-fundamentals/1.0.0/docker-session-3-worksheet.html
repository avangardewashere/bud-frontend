Theory

0/4

You've been running other people's images for two sessions. Now you write the recipe. Keep this block short — the hands-on is where it lands.

FROM picks the base. WORKDIR sets the directory for everything after it. COPY brings files in. RUN executes at build time. CMD executes at run time. EXPOSE documents a port and publishes nothing.

The clearest way to hold the whole file in your head: RUN happens once, while the image is being made, and its result is baked in. CMD happens every time a container starts. Mixing these up is the source of most beginner Dockerfile bugs.

The . in docker build . isn't cosmetic — the entire directory gets packaged and shipped to the daemon before the build starts. Your node_modules and .git go with it unless you say otherwise.

Each instruction's cache depends on every instruction before it. Change one thing and everything below it rebuilds. That single rule dictates the order of every Dockerfile you will ever write: things that rarely change go at the top.

Hands-on

0/9

Build the wrong version first. Feeling a 40-second rebuild for a one-line change is what makes the correct ordering stick.

The hostname it returns is the container ID — the same one you saw in docker ps last session.

mkdir docker-api && cd docker-api npm init -y npm install express

index.js

const os = require("os"); const express = require("express"); const app = express(); app.get("/", (_req, res) => { res.json({ ok: true, container: os.hostname() }); }); app.listen(3000, () => console.log("api listening on 3000"));

Read the total duration at the bottom of the build output and put it in row 1 of the table below.

Dockerfile

FROM node:22-alpine WORKDIR /app COPY . . RUN npm ci --omit=dev EXPOSE 3000 CMD ["node", "index.js"]
docker build -t myapi:naive .

Every step should say CACHED. This is the best case and it's the one you'll almost never get in real work.

docker build -t myapi:naive .

Edit the JSON response in index.js — add a field, anything. Then watch npm ci run from scratch because of it. This is the pain you're here to feel.

docker build -t myapi:naive .

Two copies instead of one. Dependencies land in a layer that only changes when package.json does. Build once cold, then edit a source line and build again.

Dockerfile

FROM node:22-alpine WORKDIR /app COPY package*.json ./ RUN npm ci --omit=dev COPY . . EXPOSE 3000 CMD ["node", "index.js"]
docker build -t myapi:v1 . # edit a line in index.js, then: docker build -t myapi:v1 .

Rows 3 and 4 are the same change to the same code. The gap between them is the entire value of this session.

For row 5, run npm install dayjs first so package.json and the lockfile both change.

Note the "transferring context" size in the build output before and after. With node_modules and .git excluded it usually drops by an order of magnitude.

.dockerignore

node_modules npm-debug.log .git .gitignore .env Dockerfile .dockerignore README.md

First run has EXPOSE 3000 in the image and still refuses the connection. Only -p opens a door. EXPOSE is a note to whoever reads your image.

docker run -d --name api myapi:v1 curl localhost:3000 docker rm -f api docker run -d -p 3000:3000 --name api myapi:v1 curl localhost:3000

With only CMD, anything you pass to docker run replaces it entirely. Swap to the split form and your arguments get appended to node instead of replacing it. That's the whole distinction.

docker run --rm myapi:v1 node --version

Dockerfile — replace the last line

ENTRYPOINT ["node"] CMD ["index.js"]
docker build -t myapi:v2 . docker run --rm myapi:v2 --version

Not "# copy files" — say why that line is in that position. If you can't justify a line's placement, you've found the thing you didn't understand yet.

Use your own two numbers from rows 3 and 4. Concrete beats abstract, and you now have the measurement.

Two failures you'll hit today.

Without a .dockerignore, your host node_modules gets copied into the image and overwrites what the build installed. Native modules compiled on your machine won't run on Alpine Linux, so the container starts and immediately crashes with a confusing binary error.

npm ci requires package-lock.json. If you write COPY package.json ./ instead of COPY package*.json ./, the install fails with a message about a missing lockfile — and it fails at build time, which is the good kind of failure.
