Configuration, environments, and secrets

A lighter session after two heavy ones. Mostly careful reading, one experiment that finds a secret you thought you deleted, and a config split you'll reuse in every project.

Theory

0/4

Your stack works. Now it needs to work differently in three places without you editing files between deploys — and without leaking anything.

This one trips up nearly everyone. A .env file in your project directory is read by Compose itself, to substitute ${VALUES} into the Compose file before anything starts. An env_file: entry is a list of variables handed to the container's environment. Different consumers, different timing, and a variable in .env does not automatically appear inside your container.

Roughly, from weakest to strongest: the image's own ENV, then env_file, then environment in the Compose file, then anything passed on the command line. Don't memorise it — you'll derive it experimentally in the first hands-on step, which sticks far better.

Layers are content, not history — deleting a file in a later instruction doesn't remove it from the layer that created it, it just hides it from the final filesystem. Anything set with ENV is plainly readable via docker history. Anyone who can pull the image can recover both. There's no un-publishing a leaked image either; the fix is always rotating the credential.

Compose merges files in the order you pass them, with later ones winning. compose.override.yaml is loaded automatically alongside the base, which makes it the natural home for development-only settings. Production gets an explicit file you name with -f. The base file holds what's true everywhere.

Hands-on

0/8

Steps 1 and 2 use a throwaway probe container so you're not debugging your real stack while learning the rules.

Build the probe, then run it and remove one source at a time — comment out environment, rerun, comment out env_file, rerun. Each result reveals the next rung down.

Dockerfile.probe

FROM alpine ENV GREETING=from-dockerfile CMD ["sh", "-c", "echo $GREETING"]

probe.env

GREETING=from-env-file

compose.probe.yaml

services: probe: build: context: . dockerfile: Dockerfile.probe env_file: - probe.env environment: GREETING: from-compose-environment
docker compose -f compose.probe.yaml run --rm --build probe docker compose -f compose.probe.yaml run --rm -e GREETING=from-cli probe

Put a variable only in .env and run the probe: nothing. Then reference it explicitly in the Compose file and run again: it arrives. That's the whole distinction, in two runs.

.env

DOTENV_VALUE=from-dotenv
docker compose -f compose.probe.yaml run --rm probe sh -c 'echo "[$DOTENV_VALUE]"' # now add to the probe service: environment: { GREETING: "${DOTENV_VALUE}" } docker compose -f compose.probe.yaml run --rm probe

The ENV value shows up in the build history in plain text. The 10MB file is deleted in the next instruction and still accounts for the image's size, because the layer that wrote it is still there. Neither of these is recoverable by editing the Dockerfile afterwards.

Dockerfile.leak

FROM alpine ENV API_TOKEN=super-secret-12345 RUN dd if=/dev/urandom of=/big-secret.bin bs=1M count=10 2>/dev/null RUN rm /big-secret.bin
docker build -f Dockerfile.leak -t leaky:v1 . docker history --no-trunc leaky:v1 docker image inspect leaky:v1 --format '{{json .Config.Env}}' docker run --rm leaky:v1 ls /big-secret.bin docker images leaky:v1

Compose mounts each secret at /run/secrets/<name> inside the container. The value is never in the image, never in the environment, and never in your Compose file — only a path is. Your app reads the file at startup.

compose.yaml — additions

services: api: secrets: - db_password environment: DB_PASSWORD_FILE: /run/secrets/db_password secrets: db_password: file: ./secrets/db_password.txt
mkdir -p secrets && echo "dev-password-not-real" > secrets/db_password.txt echo "secrets/" >> .gitignore docker compose up -d api docker compose exec api cat /run/secrets/db_password docker compose exec api env | grep -i password

Every literal value in compose.yaml becomes a ${VARIABLE} reference. Commit .env.example with the keys and placeholder values, gitignore the real .env. Then check the merged result — config resolves every substitution so you can see what Compose will actually run.

printf ".env\n" >> .gitignore docker compose config docker compose config | grep -i -A2 environment

Check docker compose config output before committing anything — if a real secret appears in it, it's in a file you're about to push.

The base holds what's true everywhere. The override adds bind mounts, the dev command, and published ports — and loads automatically. Production is explicit and never accidental.

compose.override.yaml — dev, auto-loaded

services: web: build: dockerfile: Dockerfile.dev command: npm run dev volumes: - .:/app - /app/node_modules - /app/.next environment: WATCHPACK_POLLING: "true"

compose.prod.yaml — explicit

services: web: restart: unless-stopped environment: NODE_ENV: production api: restart: unless-stopped db: restart: unless-stopped
docker compose up -d --build docker compose -f compose.yaml -f compose.prod.yaml config docker compose -f compose.yaml -f compose.prod.yaml up -d --build

Change NEXT_PUBLIC_API_URL in .env, restart the service, and load the page: the old value. Rebuild and load again: the new one. You proved this in session 4 with a single container; here it's the version you'll actually hit, because restart is what your fingers reach for.

docker compose restart web # load the page, read the value docker compose up -d --build web # load it again

Worth doing once deliberately so the habit exists. Anything matching a credential pattern that git is still tracking needs removing from the index, not just from disk.

git status --short git ls-files | grep -E "\.env$|secret|\.pem$|credential" git check-ignore -v .env secrets/db_password.txt

Deliverable

0/3

Next session pushes images to a public registry. Everything here is what stops that from being a mistake.

Every key your app reads, with a placeholder value and a one-line comment on what it's for. This is the file that determines whether someone can run your project in five minutes or an hour.

Three rows: your machine, CI, the production host. For each, what holds the value and what must never hold it. You need this written before session 9, when a pipeline starts needing registry credentials.

Remove leaky:v1, the probe image, and the scratch files. Keep Dockerfile.leak in a notes folder if you like — it's a good thing to show someone.

Two quiet ones.

docker compose restart restarts the process with the existing image. It does not rebuild, so any change to a build argument — including every NEXT_PUBLIC_ variable — is invisible until you add --build. You will lose time to this at least once, and the symptom is a value you're certain you changed.

Compose reads .env from the project directory automatically, with no flag and no mention in your Compose file. A leftover .env from another experiment can silently change which database your stack connects to. When something is configured in a way you can't explain, docker compose config shows you the truth.
